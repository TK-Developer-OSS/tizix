# x86-i386-unreal を実機(古いノート PC)で動かす手順

QEMU で動くことは確認済み(`arch/x86-i386-unreal/tools/test_interactive.py` が FAIL 0)。
ここでは USB メモリから実機を起動する手順を、1 ステップずつ書く。

## 先に知っておくこと

- **画面には何も出ない。** コンソールは COM1(シリアルポート、I/O 0x3F8、115200bps、8N1)。
  実機では、シリアルポートのある古いノートと、別の PC をクロス(ヌルモデム)ケーブルでつなぐ。
- **ブートは BIOS(レガシー)方式。** UEFI のみ(CSM なし)の機種では起動しない。
- イメージは 1.44MB のフロッピー形式(`arch/x86-i386-unreal/disk/floppy.img`)。

## ステップ 1: USB メモリを確認する

USB メモリを差してから、次を実行する。

```
lsblk -o NAME,SIZE,MODEL,TRAN,MOUNTPOINT
```

`TRAN` が `usb` の行が USB メモリ。名前(`sdb` など)をメモする。
**内蔵ディスクと間違えると中身が消える。** 迷ったら Claude に出力を貼って見てもらう。

## ステップ 2: USB メモリに書き込む(中身は全部消える)

`sdX` を、ステップ 1 でメモした名前に置き換える(`sdb1` のような番号付きではなく、`sdb`)。

```
sudo umount /dev/sdX* 2>/dev/null
sudo dd if=arch/x86-i386-unreal/disk/floppy.img of=/dev/sdX bs=512 conv=fsync status=progress
```

## ステップ 3: シリアルでつなぐ

- ノートの COM1 と別の PC を、クロス(ヌルモデム)ケーブルでつなぐ。
- 別の PC 側でターミナルを開く(例: `screen /dev/ttyUSB0 115200`)。
  設定は 115200bps、8N1、フロー制御なし。

## ステップ 4: 実機を USB から起動する

1. USB メモリを差して電源を入れ、BIOS の起動メニューを出す(機種により F12 や Esc)。
2. 起動デバイスに USB を選ぶ。
   - 「USB-FDD」「USB Floppy」と出るなら、それを選ぶ(このイメージはこれ向け)。
   - 「USB-HDD」だけだと、起動しないことがある(パーティションテーブルがないため)。

## うまくいかないとき(切り分けの順番)

1. BIOS が USB から読み始めるか(アクセスランプや、ブートの文字が出るか)。
2. 別の PC のシリアルに `tizix stage2` の文字が出るか。
3. `[/root]#` のプロンプトまで出るか。

どこで止まったかを Claude に伝えれば、次を調べる。

## 補足

- シリアルポートのないノートでは、VGA 画面と PS/2 キーボードのコンソールを新規に作る必要がある(未着手)。
- コマンドラインは 48 文字までが仕様(全アーキ共通)。

## ThinkPad R40(IBM、BIOS 機)向けの準備メモ(2026-10-18、Claude)

R40 の仕様は記憶ベース。**「要実機確認」の印の付いたものは実機で確かめる**。

### 前提(分かっていること / 要確認)
- BIOS ブート(UEFI ではない)。i686 系(Pentium 4-M 世代)の 32bit CPU で、リアルモードはそのまま動く。PIT(8254)・PIC(8259)・8042 キーボードコントローラ・VGA テキスト(B800:0)は標準品相当。
- 内蔵フロッピーは無い(UltraBay 用 FDD は別売)。内蔵 HDD は 2.5 インチ IDE(ATA)。光学ドライブはある(UltraBay 想定)。
- シリアルポート(COM1)は**無い**(TK 確認。パラレル D-sub25 と VGA D-sub15 のみ)。起動時に 16550 を検出して無ければ COM1 を使わない作りにする(#174)。
- キーボードは PS/2(8042)。配列は **JP か US か要確認**。現在の scancode 変換表は US 配列(`console_vga.c`)。JP だと `@ : ^ _ ( )` などの記号の位置が違うので別表が要る。
- USB ブート(USB-HDD / USB-FDD)に対応するかは BIOS のバージョン次第(**要実機確認**)。

### 起動方法の候補(上ほど手軽)
1. **ブータブル CD(El Torito のフロッピーエミュレーション)**: 現在の `floppy.img`(1.44MB)をそのまま CD に焼く。BIOS がフロッピー(ドライブ番号 0x00)として見せるので、`bios13.s`(18/2/80 の幾何・ドライブ 0)は無改造で動くはず。`xorriso`/`mkisofs` で作れる。CD-R と光学ドライブがあれば最短。
2. **USB-FDD エミュレーション**で USB メモリに `floppy.img` を `dd`(BIOS が対応する場合。ドライブ番号 0x00 で見える)。
3. **内蔵 HDD / USB-HDD**(ドライブ番号 0x80、LBA/CHS が 1.44MB と違う)。MBR とパーティション、INT 13h 拡張(AH=42h)が要る = 大工事(#175)。最後。

→ 最初の実機試験は 1(CD)か 2(USB-FDD)で、**ブートローダとカーネルは今のまま**、コンソールだけ #174 の VGA+キーボード版(`CONSOLE=vga`)にする。

### 実機で先に潰すべきリスク
- **BIOS が INT 13h の中で sti する可能性**: QEMU(SeaBIOS)では問題が出ていないが、実機の BIOS は違うかもしれない。カーネル(syscall 途中)に PIT 割り込みが入る恐れがある。対策案(INT 13h の前後で PIC の IRQ0 をマスク)は `diff/bios13_guarded.s.txt` に作ってある。**既定のビルドには入れていない**: COM1 版の回帰は通るが、`CONSOLE=vga` と組み合わせると `ls` が空になる不具合が出た(原因未解明)。実機でディスク読み書き中に化ける・止まる症状が出たら、これを入れて再検討する。
- **VGA 版コンソールの .bss 溢れ**: `CONSOLE=vga` の回帰試験が `ls` で止まる(カーネルが大きくなって配置が変わり、既存の溢れが出る疑い)。実機投入前に原因を特定する。
- **ユーザースタックが約 200B**(引数領域 0xFF00 の直下まで)。深い再帰や大きいローカル配列で引数を壊す。実機でも同じ。
- **FatFs の部分書き込み/整数セクタ書込の失敗**(#166): 大きいファイルの cp は遅く(約 450B/s)、ブロック書込は一部欠落する。実機の IDE/CD ではなくフロッピー(エミュレーション)経由なので、実機でも同様に遅いはず。

### 実機に持っていくもの(チェックリスト)
- [ ] CD-R(または USB メモリ)と、R40 の光学ドライブ / USB ブート可否の確認
- [ ] 画面(VGA)に `tizix stage2` → `[/root]#` が出るか(出なければ止まった段階を撮影)
- [ ] キー入力(US/JP の記号を一通り)
- [ ] `ls`、`echo > file`、`cat`、`vi` が動くか(floppy エミュレーション上)

### 追記(TK 回答 2026-10-18)
- キーボードは**日本語(JIS)配列**。`console_vga.c` の変換表を JIS 106 キー(スキャンコードセット 1)に差し替え済み(`@ : ^ ` ` ` * ' ( )` など、ろ `\ _`、¥ は `\` で代用)。半角/全角・変換・無変換は無視。**実機で記号を一通り打って確認すること。**
- **IBM 純正の USB FDD がある** → **第 1 候補は「実物のフロッピーディスク」**: 開発機(USB FDD を接続)で `sudo dd if=arch/x86-i386-unreal/disk/floppy.img of=/dev/sdX bs=512 conv=fsync`(sdX は USB FDD。`lsblk` で TRAN=usb を確認)し、R40 の USB ポートに FDD を挿して BIOS の起動順で USB FDD を選ぶ。実機の BIOS からはドライブ 0x00 のフロッピーとして見える(エミュレーションではなく本物の FDD)ので、`bios13.s` の 18/2/80 の幾何がそのまま合う。**FDD は QEMU の `-boot a` と同じ形**で、いちばん確実。光学ドライブは「ついているが動くか不明」なので予備(CD ブートは後回し)。
- **訂正: R40 にシリアルポートは無い**(TK 確認。背面は D-sub 25 ピン = パラレルポート、D-sub 15 ピン = アナログ VGA)。したがって **実機のコンソールは画面(VGA)+ PS/2 キーボードだけ**。COM1 は存在しない前提で、起動時の 16550 検出が「無し」になり COM1 を使わない(`console_vga.c` はそう作ってある)ことが必須。QEMU の回帰試験は従来どおり COM1 版(既定の `console.c`)で行い、実機用は `CONSOLE=vga`。ログを別 PC に取る手段は無い(必要ならパラレルポート出力などを後で検討。今回は対象外)。
- **R40 にはイーサネットがある**(有線 NIC)。tizix の x86-i386-unreal には現状ネットワークが無い(syscall 36〜46 は gcc/フラット系のみ。16bit リアルモードの NIC ドライバ + TCP が要る = 大きい課題)。**今回の実機試験の対象外**、将来の別カード(ESP32 AT 経由か NIC ドライバか)として記録するだけにする。

### 追記: R40 の内蔵 HDD は不調(TK 報告 2026-10-18)
- 内蔵 HDD が異音を出し、XP が起動後(コントロールパネルを開いたところ)で青画面になった。HDD 故障の疑い。
- 方針: **tizix の実機試験は HDD を使わない**(USB FDD 起動のみ)。#175(HDD/USB ブート)は優先度を下げる。
- 起動時の BIOS が HDD 検出で長く待つ場合は、BIOS セットアップで HDD を無効にするか、物理的に外す。
- XP 内のデータが必要なら、tizix の試験より前に別 PC へ救出する(HDD への書き込みはしない)。

### 追記: コンソールの統合(2026-10-19)
- 以前の「COM1 専用の console.c」と「画面版 console_vga.c」の分離を廃止し、`arch/x86-i386-unreal/console.c` 1 本にした
  (`CONSOLE=vga` の切り替えも廃止)。**出力は常に画面(VGA)と COM1(16550 を起動時に検出し、無ければ無効)の両方**、
  入力は COM1 とキーボード(8042 直読み、JIS 配列)のどちらからでも受ける。
- このため QEMU(`make ARCH=x86-i386-unreal clean all run`、COM1 に出る)と実機(画面+キーボード)は同じビルド。
  上の記述にある `console_vga.c` / `CONSOLE=vga` は旧名称(現在は console.c に統合済み)。
