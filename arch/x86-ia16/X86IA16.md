# x86-ia16: スタックの扱いの問題点(議論用メモ)

作成 2026-10-23(Claude)。TK の指示「スタックの扱いについての問題点を X86IA16.md に出して、セッションを仕切り直して徹底議論する」に基づく。
次のセッションがこれ 1 枚から議論を始められるように、事実・測定値・選択肢・未決事項をまとめた。**この文書は議論の素材であり、結論ではない。**

関連: task #189(tzcc を ia16 のコンパイラに)・#190(CPU 判定)・#193(COM のドライバ化)。コードは `crt0.s`、`sysfile.c`、`kmain.c`、`plat.h`。

---

## 1. 現状の仕組み(事実)

### 1.1 スタックは 3 種類ある

| 種類 | 置き場所 | 使う人 | 切り替えの記憶 |
|---|---|---|---|
| ① プロセスのスタック | 各プロセス自身のセグメント(プール 4KB ブロック、CS=DS=ES=SS) | ユーザーコード | タイマ割り込みで切り替わるとき、`_isr08` が SS:SP を `sp_tbl[]` / `ss_tbl[]`(`kwork` 内、スロットごと)に記憶 |
| ② syscall スタック | **カーネルのセグメント**(0x1000)の `.bss` 内 `sc_stack`。**スロットごとに 1KB × 24 = 24KB** | `int 0x80` に入った間のカーネル C コード | `_isr80` が、入口で呼び出し元の SS:SP を `sc_css[]` / `sc_csp[]`(スロットごと)に保存し、`SS=DS=ES=KSEG`、`SP=sc_stack の自分の枠の上端` に切り替える |
| ③ カーネル本体のスタック | カーネルのセグメントの上端(`SP=0xFFFE` から下向き) | `kmain` / `init` / slot 0(idle)、起動時 | slot 0 の `sp_tbl` / `ss_tbl` |

- `_isr80` の入口で、`int` によりすでに IF=0。`sys_call()`(C)を呼び、戻ったら呼び出し元のスタックへ戻す。
- 引数は一旦、グローバル `sc_ax` ... `sc_cseg`(スロット共有)に置き、直後にスタックへ `push` する(IF=0 のあいだに行うので衝突しない)。

### 1.2 なぜ syscall の間だけ別のスタックにするのか(根)

- **ia16-gcc(`-mcmodel=tiny`)の C は SS == DS を前提にする。** ローカル変数のアドレスを関数に渡すと、その相手は DS からのオフセットとして解釈する。
- プロセスのスタック(SS=プロセスのセグメント)のまま、カーネルの C(DS=KSEG)を呼ぶと、ローカルのポインタが別のセグメントを指してしまう。
- したがって syscall の間は `SS=DS=KSEG` にして、**カーネルのセグメントの中にスタックを持つ**必要がある。
- z80 は、カーネルもプロセスも 1 つの 64KB を共有するので、「SP をプロセスの領域に移すだけ」で済む。ia16 は、セグメントが分かれているので、同じことができない。

### 1.3 なぜスロットごとに持つのか

- syscall は途中で**待つ**ことがある。待っているプロセスのスタックの中身を、他のプロセスの syscall に壊されないために、スロットごとに別のスタックを持つ(#143、`PERSLOT=1`)。
- 待つ場所(`KYIELD()` = `sti; hlt; cli`)の一覧(いずれも syscall の途中で呼ばれうる):
  - `src/io.c` の `kgetchar`(入力待ち)と `con_break`(Ctrl+C の確認)
  - `src/pipe.c`(パイプの読み書き待ち、`krun_pipe` の子の終了待ち)
  - `src/kernel.c`(`proc_block`、スリープの待ち)
  - `arch/x86-ia16/sysfile.c` の `ksleep`(syscall 51)
  - 外部シェルの前景待ち(`sh.bin` が `con_break` を呼ぶ)
- さらに、`IRQ_ON()` が、syscall の途中の任意の場所で割り込みを許可しうる(`io.c` の `kputchar` の `IRQ_OFF/ON` の対など)。つまり、**待ちの場所以外でも、タイマに奪われうる**。

## 2. 測定値(2026-10-23、QEMU)

- `kernel.bin` = 24,660 B(縮小前 41,174 B)。`__bss_end` から上端までが、カーネル本体のスタック領域。
- `free` に表示している(`syscall 53 sel 10 / 11`、起動時に `0xA5` で埋めて、残っているパターンの長さを見る)。
  - syscall スタック(スロットごと)の最小の余裕: 512B のとき **92B**(外部シェルの `krun_pipe` などで使用 420B)、1KB にして **554B**(使用約 470B)。
  - カーネル本体のスタックの余裕: **5.8KB**(`sc_stack` を 24KB 持った状態)。
- `krun_pipe` / `kexec_argv` / `f_*`(自前 FAT12)/ `builtin_try` が、深い経路。
- 参考: syscall スタックを 24KB 持つせいで、カーネルのセグメントの 3 分の 1 強(24KB / 64KB)が、スタックに消える。

## 3. 問題点

### P1. メモリの浪費(syscall スタックが 24KB)
- 24 スロット × 1KB を、常に持つ。実際に同時に待っている syscall は、せいぜい数個。
- スロット数を増やす(#186 の方針)ほど、カーネルの bss が線形に増える。**スロット数とカーネルの余裕が、トレードオフになっている。**
- PC/XT(256KB)や「RAM 64KB にすべて載せる」(TK の発言。意味は未確認)を目指すと、致命的に重い。

### P2. 深さの上限が、静的で、壊れ方が静か
- 各スロットのスタックの大きさが固定で、あふれると、**隣のスロットのスタック(`sc_stack` の中で隣り合う)を、黙って壊す**。ガードがない。
- 現状、`free` の headroom を、人が見ているだけ。起動時のパターン埋めでの測定(`x86_scstk_headroom`)は、診断用で、実行時の保護ではない。
- 深い経路を足すたびに、余裕が減る(実際に、外部シェルの導入で 554B → 92B まで下がった)。

### P3. 割り込みが、syscall の途中の任意の場所に入る
- `IRQ_ON()` が、syscall の途中で IF を立てる(1.3)。ISR(`_isr08`)は、そのとき走っているスタック(syscall スタック)に、さらに 24B ほど積む。
- ISR が、`ss_tbl`=KSEG のスロットを、切り替えて他へ移す。深さの見積もりに、ISR のぶん(24B + 呼ぶ C の `plt_interrupt`)を含める必要がある。

### P4. 「SS == DS」を前提にするコンパイラが、設計を縛っている(根本)
- ia16-gcc 6.3.0 は、SS と DS を分けて扱えない。**プロセスのスタックの上で、カーネルの C を直接走らせられない**ことが、P1〜P3 の根。
- `-Os` などの最適化でも、near ポインタを隣の 32bit 引数と融合して far ロード(`les`)を出すバグがあり、`-O2` 系以外を使えない。コンパイラ側の制約が、ほかにも設計を縛っている。
- z80 では、tzcc が `iy_reg`(IY 相対の位置非依存コード)を出して、コンパイラ側で解決した。ia16 は、まだ、既製の ia16-gcc のまま。

### P5. 関連する小さな問題
- `sc_ax` などの引数のグローバルは、スロット共有。IF=0 の間だけ成り立つ前提(`push` で直ちに写す)。
- `kill` で、待っている最中のスロットを解放しても、その syscall スタックを、誰も片付けない(今は、枠が固定なので、実害は小さい)。案 D を取る場合は、退避バッファの解放が、新たに要る。
- `x86_irq_depth` / `x86_irq_was`(`IRQ_OFF/ON` の入れ子の記憶)は、全体で 1 つ。スロットが、入れ子の途中で切り替わると、他のスロットの状態を、巻き込みうる(未検証)。

## 4. 選択肢

| 案 | 内容 | カーネルの bss | 変更の大きさ | 主な危険 |
|---|---|---|---|---|
| 現状 | スロットごとに 1KB | 24KB | なし | P1・P2 |
| A | syscall の深さを減らし、スロットごとのスタックを 512B にする | 12KB | 小〜中 | 余裕が 92B のまま。静かに壊れる |
| A' | スロット数を減らす(たとえば 16) | 16KB | 小 | スロット数が減る |
| B | ブロックする syscall を「やり直し方式」に作り直す。待つときは、`int 0x80` を巻き戻して再実行。スタックは常に空なので 1 本 | 約 1〜2KB | 大 | 副作用のある syscall(パイプの書き込み、`krun_pipe` の起動)の再実行の扱い。待つ場所が多い |
| C | スタックのプール。syscall の入口で 1 本借りる。無ければ入口でやり直し | 約 8KB | 中 | 待っている syscall がプールを握り、他が進めず**デッドロック**しうる |
| **D** | **スタックを 1 本にして、切り替えるとき(`_isr08`)に、使っている部分だけを退避バッファへ写し、戻すときに同じアドレスへ写し戻す** | 共有 1.5KB + 退避プール(6×1KB 程度) ≈ 7〜8KB | 中(`_isr08` の変更が中心) | 退避バッファが尽きたときの扱い。深さが退避バッファを超えたとき |
| **E(根本)** | **tzcc の ia16 バックエンドが SS と DS を分けて扱う。** ローカルは BP 相対(= SS)、グローバルは DS、ローカルのアドレスは SS 付きの型または禁止。カーネルが、プロセスのスタックの上で、そのまま走る(DS だけ KSEG に切り替える) | 0(syscall 専用のスタックが不要) | 非常に大(コンパイラ。#189) | 時間。カーネルの C に、ローカルのアドレスを取る箇所が多い(`FIL fp` など) |

### 案 D の設計の骨子(実装前の検討済みの内容)
- `_isr80`: 常に `SP = sc_stack_top`(共有の 1 本)。引数のグローバルは、そのまま。
- `_isr08`: 切り替え元の SS が KSEG で、SP が `sc_stack` の範囲内なら、`[SP .. sc_stack_top)` を、空いている退避バッファへコピー(`rep movsb`)。切り替え先が同様なら、その退避バッファから同じアドレスへ戻してから `iret`。同じスロットへ戻るだけなら、何もしない。
- 退避バッファが無い、または深さが 1 枠を超える場合: 切り替えない(同じスロットを続行)。
- 注意: `BP` を基準にするアドレッシングは、既定が SS なので、退避中は `bx / si / di` だけを添字に使う。コピーの間は、スタックを使わない(`push` / `call` をしない)。`sc_exit` は退避しない(`dl=0xFF`)。`kill` で、バッファを解放する(`x86_proc_release`)。
- slot 0(idle)のスタックは、カーネル本体のスタック(0xFFFE)なので、範囲外で、対象にしない。
- 見積もり: 17KB 前後の削減。

## 5. 議論したい論点(未決)

1. **目標は何か。** (a) カーネルの bss を減らす(P1)、(b) 壊れ方を静かにしない(P2)、(c) スロット数を増やす、(d) PC/XT や「RAM 64KB」(意味未確認)への適合、のどれが主か。
2. **つなぎ(案 D)を実装するか、E を待つか。** D は、E が実現したら不要になる。E は、時間が大きい(#189 の優先度は LOW)。
3. **E の設計。** tzcc の ia16 バックエンドで、SS を分けた型システムをどうするか(`__seg_ss` 相当 / ローカルのアドレス取得の禁止 / 暗黙の far)。カーネルの C のうち、ローカルのアドレスを取る箇所の数。
4. **「RAM 6KB(または 64KB)にすべて載せきれたら、とりあえずのゴール」**(TK の発言)。この目標は、スタックの設計にどう効くか。意味の確認が先。
5. **ガードの入れ方。** 実行時のスタック溢れの検出(たとえば各枠の底に番兵、syscall の出口で検査)を、案とは別に入れるか。
6. **PC/XT 基準**(最低基準)との関係。8088 での速度(退避のコピーが、4.77MHz でどれだけ重いか)。
