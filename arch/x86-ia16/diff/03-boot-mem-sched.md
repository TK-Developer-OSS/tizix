# #170 ブート・メモリマップ・スケジューラの比較 (x86-ia16 vs m68k-mega)

本ドキュメントでは、`arch/x86-ia16` と、GCC系ポートの代表例である `arch/m68k-mega` の実装を対象に、ブートローダ、メモリマップ、ユーザープロセス配置、スケジューラ、およびシステムコール入口の各項目について対比・比較を行う。

---

## 1. 項目別の対比表

| 項目 | arch/x86-ia16 | arch/m68k-mega (gcc系) |
|---|---|---|
| **ブート** | **2段階ブートストラップ**<br>・stage1: VBR（セクタ0、512B）が stage2（LBA 1〜8）を `0x0800:0000` にロードして far jump。<br>・stage2: CHSループで kernel blob を `0x1000:0000` にロードしてカーネルへ far jump。 | **外部ローダ / ROMレス構成**<br>・ハードウェア（Arduino Mega2560）またはシミュレータが起動前に SRAM へバイナリを直接書き込む。<br>・ベクタテーブル（vector 0-1）を参照して直接 `_start` へジャンプ。 |
| **カーネルのメモリマップ** | **16bit実モード 64KBセグメント**<br>・`CS = DS = SS = 0x1000`<br>・小モデル（`-mcmodel=tiny` 相当のセグメント内コンパクト配置）、高位側 `0xFFFE` にスタックを配置。 | **32bitフラットメモリモデル**<br>・`0x000000` 起点で 1MB SRAM を使用。<br>・ベクタ、`.text`, `.rodata`, `.data`, `.bss` を連続配置。スタックは RAM 終端（`__stack_top`）から下へ伸長。 |
| **ユーザープロセス配置** | **セグメントベースの隔離モデル**<br>・slot `n` (0..7) ↔ セグメント `(n+1) * 0x1000`<br>・slot 0 は kernel/idle (`0x1000`)、slot 1〜7 はプロセスセグメント (`0x2000`〜)。 | **フラットメモリの動的ロード・スロット管理**<br>・固定スロット（または `PLAT_SLOT_ADDR`）でメモリ空間を区分け。<br>・PC相対コード（`-mpcrel`）により動的再配置に対応。 |
| **スケジューラ (タイマ / KYIELD / 協調)** | **8254 PIT / IRQ0 によるプリエンプション**<br>・タイマ: 8254 PIT ch0 (100Hz) → IRQ0 (INT 08h) で `_isr08` がレジスタ退避、tick進行、ラウンドロビンで `sp_tbl`/`ss_tbl` を切替。<br>・KYIELD: `sti; hlt; cli` による協調動作。 | **レベル6タイマ割込み / TRAP #1**<br>・タイマ: レベル6タイマ割込み (TICK_HZ、例: 25Hz) → `irq6_handler` で全レジスタ退避、`plt_interrupt` と `sched_tick_sp` により SP を切替。<br>・KYIELD: `TRAP #1` (`vector 33`) による自分からのCPU譲渡。 |
| **Syscall 入口** | **INT 80h ソフトウェア割込み**<br>・`_isr80` ハンドラ。<br>・呼び出し元スタックから引数をカーネルグローバルに退避し、SS/SPをカーネル専用 syscall スタック (`sc_stack`) に切り替えてから C の `sys_call` を実行。 | **TRAP #0 ソフトウェアトラップ**<br>・`vector 32` (`trap0_handler`)。<br>・68000の例外・トラップメカニズムを利用してシステムコール（`kexec`）を起動。 |

## 2. x86-ia16 固有の制約

1. **64KBカーネルの制約**: 
   `CS = DS = SS = 0x1000` の 64KB セグメントの枠内に、カーネルの text, rodata, data, bss、およびカーネル用の一時領域のすべてが収まる必要がある（Small / Tiny モデル）。
2. **セグメントとポインタの扱い**: 
   16bit実モードのため、データポインタ（near pointer）は同一セグメント内（64KB）に限定される。プロセス間スイッチ時には SS セグメントの切替えが必須となる。
3. **syscall専用スタック (`sc_stack`) の必要性**: 
   ユーザープロセスのスタックのままカーネルの C コード（`sys_call`）を実行すると、`-mcmodel=tiny` の前提（`SS == DS == CS`）やスタックサイズ不足が生じる。そのため、アセンブリ側（`_isr80`）でカーネル専用のスタック (`sc_stack`) に一度切り替える実装が必要となる。
4. **BIOS / 16550 UART とブートの制約**: 
   stage1 (512B VBR) のサイズ制限（512バイト以内）および stage2 での BIOS INT 13h / シリアル直叩きによるローディングの実装が必要不可欠である。

---

## 3. 共通設計へ寄せる際の障害（5項目以内）

1. **メモリモデル・ポインタ幅の相違**:
   フラット32bit（m68kやgcc系）と16bitセグメント（x86-ia16）では、ポインタのサイズやアークテクチャ固有のレジスタ保存・セグメントレジスタ管理の抽象化が困難。
2. **システムコール機構の差異**:
   x86-ia16 はソフトウェア割込み (`INT 80h`) を用いるが、アーキテクチャによってはトラップ命令（m68k の `TRAP #0` など）やシステムコール専用ハンドラの仕組みが異なり、共通化が難しい。
3. **ブートローダとストレージアクセスの差異**:
   x86-ia16 は VBR (FAT12/CHS) や BIOS に依存する一方、m68k-mega 等はボードのROM/SRAM書き込みやシミュレータ前提であり、ブート手順の共通化ができない。
4. **コンテキストスイッチとスタック管理**:
   セグメントレジスタ（SS）とスタックポインタ（SP）の両方を管理する必要がある x86-ia16 のスレッド切替と、フラットメモリで SP のみを切り替えるアーキテクチャの間で、スケジューラの共通化（`sched_tick_sp` 等の共通化の限界）。
5. **コンパイラ差異と移植シム (`plat.h`) の制約**:
   ia16-gcc 特有のメモリモデルや属性の差異を吸収するために多くのマクロシム（`__sdcccall` 等の空定義や `KYIELD` の定義）が必要になり、コードの共通化における障害となる。

---
*注記: 本ドキュメントの内容はすべて `arch/x86-ia16` および `arch/m68k-mega` のソースコード（stage1.s, stage2.s, crt0.s, plat.h, link-kernel.ld 等）の実態に基づく事実である。*
