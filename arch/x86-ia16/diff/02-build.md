# #169 ビルド構成の比較 (x86-ia16 Makefile vs common-gcc.mk)

## 1. 共通 mk が提供するものと x86-ia16 Makefile の対応表

| 項目 / 共通 mk (arch/common-gcc.mk) | x86-ia16 Makefile (`arch/x86-ia16/Makefile`) の対応状況 | 備考・差異 |
| :--- | :--- | :--- |
| **UCMDS** (外部コマンド一覧・ビルド規則) | 個別定義 (`TZPORT_CMDS`) と手動コピー (`obj/tzport/`) | x86-ia16 は共通 mk の `UCMDS` を使わず、`TZPORT_CMDS` を手動定義して `obj/tzport/` に `.c` や `stdio.h` をコピーしてビルドしている。 |
| **LOBJ** (共通 libc / sysfile 等) | `AOBJ` の中に個別列挙 (`$(OBJ)/libc.o`, `$(OBJ)/sysfile.o` 等) | 共通 mk では独立した変数だが、x86-ia16 ではアーキ固有オブジェクト (`AOBJ`) の中に混在して定義されている。 |
| **SOBJ** (共有カーネル中核) | `SOBJ` を定義しているが構成が異なる | x86-ia16 の `SOBJ` には `sh.o` が含まれるが、共通 mk では `sh` は外部コマンド (`sh.bin`) として扱われる。 |
| **HDRS** (ヘッダ一括依存関係) | **欠如** (`HDRS` による依存定義なし) | x86-ia16 のオブジェクト規則には共通ヘッダ群への依存 (`$(HDRS)`) が無く、ヘッダ変更時の古いオブジェクト残留リスクがある。 |
| **DISK_IMG** (ディスク像生成) | FAT12 フロッピー (`disk/floppy.img`) の個別ビルド規則 | 共通 mk は FAT16 ディスク像 (`DISK_IMG`) を前提とするが、x86-ia16 は QEMU フロッピーブート向けに VBR(stage1)・gap stage2・カーネルの `dd` 書き込みおよび `FAT_RSVD` 予算チェックを独自実装している。 |

## 2. 差異の箇条書き (事実と推測)

- **コマンド一覧 (`TZPORT_CMDS`) の手動管理とコード複製** (事実):
  x86-ia16 では `TZPORT_CMDS` にコマンド名を手書きし、`user/` から `obj/tzport/` へソースと `stdio.h` をコピーしてからコンパイルしている。一方、common-gcc.mk は `UCMDS` により `user/` から直接コンパイルする方式に移行済みである。
- **ヘッダ変更に対する依存関係の欠如** (事実):
  common-gcc.mk にはある `HDRS = $(wildcard include/*.h) ...` による一括依存定義が x86-ia16 には存在しないため、インクルードファイルを変更した際に再ビルド漏れ（古いバイナリの混入）が起きやすい構造になっている。
- **ディスク像生成とブート構成の根本的違い** (事実):
  x86-ia16 は QEMU リアルモード動作の FAT12 フロッピー (`disk/floppy.img`) を対象としており、ステージ1(VBR)、ステージ2、カーネルを `dd` で正確な LBA 位置に配置し `FAT_RSVD` のセクタ数予算チェックを行っている。一方、common-gcc.mk は FAT16 の `DISK_IMG` 生成を汎用化しているため、そのままでは x86-ia16 の二段ブートに流用できない。
- **シェル (`sh`) の配置場所の相違** (事実):
  x86-ia16 では `sh.o` がカーネル中核 (`SOBJ`) に組み込まれているが、common-gcc.mk 採用アーキテクチャでは `sh` は外部コマンド (`sh.bin`) としてディスクに格納され初期タスクから起動される。
- **コンパイルフラグ・リンカのアーキテクチャ制約** (事実):
  x86-ia16 は 16bit リアルモード専用の `-mcmodel=tiny` や、特定コンパイラバージョンにおけるバグ回避のための `-O2` 必須指定、専用リンカスクリプト (`link-kernel.ld`) を持っており、32bit フラットモデル前提の common-gcc.mk とは前提条件が大きく異なる。
- **推測**: x86-ia16 が common-gcc.mk を直接インクルードしていないのは、セグメントモデルや 16bit 特有のフラグ・二段ブート処理が common-gcc.mk の前提（FAT16、32bit フラット、外部コマンド構成）と合致しなかったためと考えられる。

## 3. x86-ia16 を共通 mk に寄せる場合の最小手順案 (5項目以内)

1. **共通ヘッダ依存の導入**: `common-gcc.mk` と同様の `HDRS` 定義およびオブジェクトコンパイル規則への適用を行い、ヘッダ変更時のビルド不整合を防ぐ。
2. **`UCMDS` 方式への部分移行**: コマンドビルドの仕組みを `obj/tzport/` コピー方式から common-gcc.mk の直接参照 (`UCMDS` / `UHDRS`) へ合わせる（ただし 16bit 用 `UCFLAGS` は維持）。
3. **ディスク像ルール（FAT12/ブート）の arch 側維持と共用化の分離**: 共通 mk のインクルードによる恩恵（`UCMDS`, `LOBJ`, `SOBJ` の共有）を受けつつ、ディスク像生成（`$(IMG)` および `dd` によるブートローダ配置）やセグメント特有の `KOBJ` 定義は x86-ia16 側 Makefile に保持・分離する。
