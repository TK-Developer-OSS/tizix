# #172 z80pack との比較 (ブロック/オーバーレイ型 vs セグメント型)

本ドキュメントでは、`arch/z80pack`（Z80 cpmsim環境、ブロック・オーバーレイ型）と `arch/x86-ia16`（8086 16bit実モード、セグメント型）のアーキテクチャ設計を比較し、共通ソース層 (`src/`) と arch 層の切り分け、および x86-ia16 における設計上の逸脱箇所と判断材料を整理する。

---

## 1. z80pack が arch 層に持つ要素と x86-ia16 の対応表

| 項目 | `arch/z80pack` (Z80 cpmsim) | `arch/x86-ia16` (8086 16bit実モード) |
|---|---|---|
| **ビルド基盤** | `common-sdcc.mk` + `arch/common-z80/*.inc` | 独自 `Makefile` (`ia16-elf-gcc`, `-mcmodel=tiny`) |
| **コンソール (`console.c`)** | ポート 0 (status) / 1 (data) の I/O ポートアクセス | I/O ポート 0x3F8 (UART) または BIOS 呼び出し等 |
| **ディスクI/O (`diskio.c`)** | cpmsim FDC ポート (10〜16) による 128B セクタアクセス | BIOS INT 13h (`bios13.s`) によるCHSアクセス |
| **メモリマップ** | 64KB Z80 空間 (`CODE_LOC=0x0120`, `DATA_LOC=0x8000`) | 16bit実モード 64KB セグメント (`CS=DS=SS=0x1000`) |
| **起動とスロット配置** | `crt0.s` (`common-z80/*.inc`)、ポート 27 でタイマ起動 | `stage1.s` (VBR) → `stage2.s` → `crt0.s` (セグメントベース slot 0..7) |

---

## 2. 「新ポートは arch 層だけで差を吸収する」原則に対する x86-ia16 の逸脱箇所

1. **システムコールディスパッチャの独自実装 (`arch/x86-ia16/sysfile.c`)**:
   - 共通 `src/sysfile.c`（あるいは `PLAT_FLAT32` 向けの共通 sysfile）を利用せず、ソフトウェア割込み (`INT 80h`) とレジスタ引数渡し、セグメント跨ぎの `farcpy` を行う独自のシステムコールディスパッチャを保持している。
2. **コンテキストスイッチ・スケジューラの独自実装 (`proc.s`, `crt0.s`)**:
   - 共通のスケジューラ機構に依存せず、8254 PIT (IRQ0 / INT 08h) を用いたセグメントレジスタ（`SS`/`SP`）切替を含むタイマ割込みハンドラ (`_isr08`) とプロセススケジューラを arch 側で直接実装している。
3. **プロセスロード・管理 (`kexec` 相当機能の arch 側内包)**:
   - 共通 `src/kexec.c` の `plat_load` / `plat_ctx` フック機構（`PLAT_FLAT32` 向け）を使用せず、64KB セグメント単位のスロット管理・ロード処理を独自に行っている。
4. **ユーザー側システムコールスタブと tzstdio (`user/tzstdio.h`, `user/usyscall.s`)**:
   - SDCC 向け共通 user 層ではなく、ia16-gcc 向けの `INT 80h` スタブ群と独自ヘッダー (`user/tzstdio.h`) を arch 配下で保持・運用している。

---

## 3. 逸脱ごとの「共通へ寄せる / arch層に残す」判断材料（事実と推測の区別）

1. **`sysfile.c` の独自実装について**:
   - 事実: ia16 は 16bit セグメント跨ぎの `farcpy` とレジスタ分割引数を必要とする一方、共通側はフラットなポインタを前提としている。
   - 判断（推測含む）: CPU アーキテクチャのポインタ・メモリモデルの乖離が大きいため、無理に共通化せず **arch層に残す** のが保守上合理的である。
2. **スケジューラ・割込みハンドラの独自実装について**:
   - 事実: 8086 のリアルモードセグメントとスタックレジスタ（`SS`/`SP`）の同時退避・切替は ia16 固有のアセンブリ制御を伴う。
   - 判断（推測含む）: ハードウェア特有の割込み・文脈切替メカニズムに強く依存するため、共通化は困難であり **arch層に残す** べきである。
3. **プロセスロード・スロット管理について**:
   - 事実: 64KB セグメント分割によるメモリ配置モデルを採用しており、32bit フラットの `PLAT_FLAT32` と設計思想が異なる。
   - 判断（推測含む）: メモリ保護・空間モデルの違いが本質的であるため、共通 `src/kexec.c` へ寄せず **arch層に残す** 方が設計の健全性が保たれる。
4. **ユーザー側 sys/libc 連携について**:
   - 事実: `INT 80h` によるシステムコール番号と引数マッピングが ia16 独自である。
   - 判断（推測含む）: 呼出規約と ABI が他のコンパイラ/アーキテクチャと一致しないため、**arch層に残す** のが適切である。
