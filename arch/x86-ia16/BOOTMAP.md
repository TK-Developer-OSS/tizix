# x86-ia16: ブートのジャンプ遷移とメモリの使われ方(アドレス別)

作成 2026-10-24(Claude)。TK の指示「VBR が POST でロードされるところから、ジャンプの遷移をアドレスで整理して」に基づく。
アドレスは**コードから読んだ事実**(stage1.s / stage2.s / crt0.s / kexec.c)。BIOS と Linux の挙動は一般的な知識で、このリポジトリでは確認していない(§5 に印を付けた)。
議論の素材であり、結論ではない。関連: X86IA16.md(スタック)、tz/README.md(tzcc 製カーネル)、task #189。

## 1. ジャンプの遷移(上から順に実行される)

| # | 誰が | 物理アドレス | seg:off | 何をする | 次へ |
|---|---|---|---|---|---|
| 0 | BIOS POST | (ROM) | | 起動デバイスのセクタ 0 を読み、DL=起動ドライブ番号を渡す *(BIOS の慣例)* | `0000:7C00` へ jump |
| 1 | **stage1 = VBR** ([stage1.s](stage1.s)) | `0x07C00`〜`0x07DFF`(512B) | `0000:7C00` | DS=ES=SS=0、**SP=0x7C00**(スタックは 7C00 の直下から下向き)。DL を `drive` に保存。INT 13h(DL<0x80 は CHS の AH=02、0x80 以上は拡張 AH=42)で **stage2 を 8 セクタ(4KB)読む** | `ljmp 0800:0000`(DL=ドライブ) |
| 2 | **stage2** ([stage2.s](stage2.s)) | `0x08000`〜`0x08FFF`(4KB) | `0800:0000` | CS=DS=0x0800、SS=0、**SP=0x7C00**。COM1 初期化・バナー。INT 12h / INT 15h(88h, E801h)の結果を **`0000:0512`〜`0519`** に置く。**カーネルを 1 セクタずつ INT 13h で `1000:bufoff` へ読む**(bufoff を 512 ずつ増やす)。起動ドライブ番号を **`0000:0510`** に置く | `ljmp 1000:0000` |
| 3 | **カーネル入口** `_start` ([crt0.s](crt0.s)) | `0x10000` | `1000:0000` | CS=DS=ES=SS=0x1000、**SP=0xFFFE**(= 物理 0x1FFFE)。**IVT を書く**: `0000:0020`(INT 08h)→`_isr08`、`0000:0200`(INT 80h)→`_isr80`。PIT ch0 を 100Hz に。PIC で IRQ0 をアンマスク。**BSS をゼロクリア**。`pid_tbl[0]=1` | `call kmain` |
| 4 | `kmain` → `init` | `0x1000:xxxx` | | con_init、メモリ情報の表示、`init()` → FAT マウント → `kexec_file("/bin/sh.bin")` | プロセスを起こす |
| 5 | **プロセス** | プールのブロック | `pseg:0100` | `.BIN` を `pseg:0100` へ、引数を `pseg:0080` へ。偽コンテキスト(12 語)を `pseg:(nblk<<12)-0x10-24` に置き、`_isr08` の `iret` で `pseg:0100` へ入る。CS=DS=ES=SS=pseg | 以後はタイマ割り込みで巡回 |

ポイント: **stage1・stage2 が使うスタックは `0000:7C00` の直下で共通**。カーネルが起動した時点で、stage1 / stage2 / 7C00 のスタックは全部不要になる(カーネルは SS=0x1000 に切り替わる)。

## 2. 物理メモリマップ(カーネル起動後)

| 物理アドレス | 大きさ | 中身 | カーネル起動後 |
|---|---|---|---|
| `00000`–`003FF` | 1KB | **IVT**(INT 08h と 80h をカーネルが書く) | 使用中 |
| `00400`–`004FF` | 256B | **BDA**(BIOS データ領域。INT 13h などが使う) | 使用中 |
| `00500`–`0050F` | 16B | 空き | 空き |
| `00510` | 1B | 起動ドライブ番号(stage2 が置く、diskio が読む) | 使用中 |
| `00512`–`00519` | 8B | メモリ情報(INT 12h / 88h / E801h の値) | 使用中 |
| `0051A`–`00FFF` | 約 2.8KB | 空き | **空き(ブロック境界に満たず未使用)** |
| `01000`–`07BFF` | 約 27KB | 空き(boot のスタックは 7C00 直下の数百バイトだけ) | **再利用可** |
| `07C00`–`07DFF` | 512B | stage1(VBR) | **不要(stage2 が走った後)** |
| `07E00`–`07FFF` | 512B | 空き | **再利用可** |
| `08000`–`08FFF` | 4KB | stage2 | **不要(カーネルへ jump した後)** |
| `09000`–`0FFFF` | 28KB | 空き | **再利用可** |
| `10000`–`1FFFF` | 64KB | **カーネルの窓**(text+data+bss、syscall スタック 24KB、カーネルスタック) | 使用中 |
| `20000`–(終端) | 可変 | **プロセスのプール**(4KB ブロック) | 使用中(プロセスが取る) |
| (終端)付近 | | EBDA(拡張 BIOS データ領域)。INT 12h の値は EBDA の手前までを返す *(BIOS の慣例)* | 触らない |
| `A0000`–`BFFFF` | 128KB | VGA(`B8000` がテキスト) | 触らない |
| `C0000`–`FFFFF` | 256KB | オプション ROM / BIOS ROM | 触らない |
| `100000`〜 | | 拡張メモリ(8086 のリアルモードからは使えない。今は未使用) | 未使用 |

## 3. 再利用の現状

- **ia16-gcc 製カーネル(既存)**: プールは `0x20000` 固定開始。**`01000`〜`0FFFF` の約 60KB は、ブート後に誰も使っていない**。
- **tzcc 製(tz/ 以下)**: [tz/kexec.c](tz/kexec.c) で、プールに**低位 15 ブロック(`01000`〜`0FFFF`)を加えた**。カーネルの窓(`10000`〜`1FFFF`)は飛ばす。1 つのプロセスが窓をまたがないよう、連続した割り当てはブロック 14 と 15 の間で切る。
  - 効果(QEMU `-m 1`、`MEMCAP_KB` で上限): 128KB で 0 ブロック(シェル起動不能)→ **15 ブロック・5 スロット(シェルもパイプも動く)**。
  - 未使用で残るのは `0051A`–`00FFF` の約 2.8KB(ブロック境界に満たない)。
- 前提: **stage1 / stage2 がカーネル起動後に不要**であること(§1 の注)。カーネル側に stage2 領域を参照するコードは無いことを確認した(crt0.s / sysfile.c / console.c / bios13.s / proc.s / diskio.c)。

## 4. 「アドレス」と「サイズ」(先の質問への答えの続き)

今のプール計算は **INT 12h が返す終端アドレス** だけを使う(RAM の実測も、穴の有無も見ない)。プールの先頭と、カーネルの窓の位置は定数。
範囲(レンジ)の表で持てば、アドレス固定の前提が消える。たとえば:

    予約: [00000,00FFF] (IVT/BDA/boot info), [10000,1FFFF] (カーネル), [EBDA〜] 
    プール = 全 RAM の範囲 − 予約  (4KB 境界に切り詰めて、連続したブロック列の組として持つ)

tz/kexec.c は、この考え方の最小形(低位ブロック列 + 高位ブロック列の 2 本)を直書きしたもの。一般化するなら、レンジ表を起動時に作る。

## 5. Linux の起動方式を真似る必要があるか *(この節は一般知識。リポジトリでは未確認)*

結論: **丸ごと真似る必要はない**。取り込む価値があるのは次の考え方だけ。

| Linux(x86 の実モード経由の起動) | 本リポジトリでの対応・取り込み案 |
|---|---|
| ブートセクタが 0x7C00 に読まれる。ローダ(LILO/GRUB 系)は自分を別の場所へ**退避して**次の段へ進むことが多い | 同じ。stage1 → stage2 の 2 段。**stage2 は 0x8000 に置き、使い終わったらその領域を回収する**(§3 でやった) |
| 実モードの setup コードと **boot params(ゼロページ)** をカーネルの手前(伝統的に 0x90000 付近)に置き、ローダが BIOS から集めた情報(メモリマップ=**E820** など)を渡す | 今の `0000:0510`〜`0519` が boot params の最小形。**E820 のレンジ表をここに置けば、アドレス固定の前提(§4)が外れる**。8086/PC-XT には E820 は無いので、INT 12h だけの機種はレンジ 1 本として扱う |
| setup が**保護モードへ切り替えて** 0x100000 の本体へ jump | **不要**。8086 のリアルモードのまま。386 以上のアンリアルモード対応は #189 / #195 の別の話 |
| 予約領域(IVT、BDA、EBDA、カーネル、initrd)を明示的に除外し、残りを空きとして扱う | §4 のレンジ表の方針と同じ |

つまり「Linux を真似る」より、**(1) 起動情報を 1 か所の構造体にまとめて渡す、(2) メモリはレンジ表で持つ、(3) 使い終わったブートローダの領域を回収する** の 3 点が要点。(3) は実装済み(tzcc 製のみ)、(1)(2) は未着手。

## 6. 未決・次の検討

1. レンジ表(§4)にするか。するなら boot params の置き場所と形式(今の 0x510〜0x519 を拡張するか、別の固定番地か)。
2. gcc 製カーネル([src/kexec.c](../../src/kexec.c))にも低位ブロックの再利用を入れるか。共有の src/ なので他アーキに影響しない `#if defined(ARCH_X86_IA16)` 内の変更になる。
3. 64KB の機械(カーネルの窓すら無い)は、配置そのものを変える話(X86IA16.md の案 E、z80 方式)。ここで整理したのは「128KB 以上」の範囲。
4. `0051A`–`00FFF` の 2.8KB の使い道(ブロック化できない端数)。

## Current layout (2026-10-29, tz build)

| physical | content |
|---|---|
| 0x0000-0x04FF | IVT, BIOS data area (0x510-0x519: memory info written by the kernel) |
| 0x0600-0x0FFF | kernel stack (segment 0, SP from 0x1000 down; about 2.3KB headroom measured at boot) |
| 0x1000-... | kernel (KSEG 0x0100): text, data, bss; loaded by stage2 |
| next 4KB boundary - end of RAM | 4KB block pool (processes, DRIVER, pipe buffers); stage1 / stage2 places are pool too |

stage2 first copies itself to the last 4KB (S2_RELOC), because the kernel is loaded over the place stage1 / stage2 started in.
The 64KB squeeze (kernel at 0x600, stack after bss, 640B stack, minimum slots) lives in `arch/x86-ia16tiny`.
