# x86-ia16: カーネルの減量メモ(実測と候補)

作成 2026-10-24(Claude)。TK の指摘「見落としがあるはず」「ドライバやプロセスに出したらいいものが残っている」「BIOS の活用はやり尽くせているか」への調査。
**数値は実測**(ia16-gcc 製カーネル、EXTSH=1)。**見積もりと書いたものは推定**。議論の素材であり、結論ではない。関連: BOOTMAP.md(ブートとメモリマップ)、X86IA16.md(スタック)、tz/README.md、task #189。

## 2. 候補(効果の大きい順ではなく、手を付けやすい順)

### A. すでに入れた・確実
1. **`--gc-sections` が効いていなかった**(今回の発見)。リンカスクリプトが `OUTPUT_FORMAT(binary)` だと、ld は `--gc-sections` を黙って無視する。ELF でリンクして `objcopy -O binary` で平らにすると、使われていない関数が落ちる。
   **gcc 製 24,738 → 22,352(−2.4KB)、tzcc 混在 28,382 → 25,744(−2.6KB)**。起動・コマンド出力・画面は基準線と一致。tz のビルド(Makefile.tz)には入れた。**既存の Makefile は触っていない**(`-ffunction-sections -fdata-sections` と ELF リンクの追加が要る)。

### B. カーネルから出せる(ドライバ/プロセス/プール)
| 候補 | 大きさ | 出し先 | 見積もり・注意 |
|---|---|---|---|
| **パイプのバッファ** | bss 4,096 | プールの 1 ブロック(z80 の `PID_PIPEBUF` と同じ) | −4KB。バッファが別セグメントになるので、pipe.c の読み書きを farcpy 経由にする。**最も手を付けやすい** |
| **syscall スタック** | bss 24,576 | (1)実行時のスロット数で確保(128KB 機は 5 スロット = 5KB)→ −19.5KB (2)案 E でそもそも無くす | (1)は crt0.s の `sc_stack` の置き方を実行時に決める変更が要る。案 E は X86IA16.md |
| **FS 一式** | text 約 12KB + bss 約 1.4KB | ドライバ(常駐するプロセス)。カーネルは要求を送る | fat12min + fatcmd + fsbackend + vfs + dev_fda + diskio。tzcc の SS≠DS で「ドライバの DS = 自分のセグメント、SS = カーネルのスタック」と動かせる見込み(ローカルのアドレスを渡さない規則が要る)。**大きな設計変更** |
| builtin(ps/kill/exit) | 648 | 外部コマンド `/bin/ps` など | EXTSH では呼ばれないのに残っている(gc 後も 648B)。何が参照しているか要調査 |
| 外部コマンドの libc の重複 | プロセスごと 0.6KB 前後 | DRIVER 的な共有(z80 は DRIVER.BIN のベクタ経由) | ブロックが 4KB 単位なので、小さなコマンドでは効果が出にくい |

### C. プロセスの側の無駄(カーネル外だが、プールの容量を食う)
| 候補 | 見積もり |
|---|---|
| ブロック粒度 4KB → 1KB(または 256B) | 小さなコマンド(スタック込み 2.7KB 前後)が 4KB を取っている。粒度を細かくすると、同じメモリで動かせるプロセス数が増える(推定 +30%) |
| スタックの最小 2KB を一律にしない | `.BIN` のヘッダにスタック量を持たせる |
| 各プロセス先頭の 256B(`pseg:0000`〜`00FF`、.COM 流儀) | 引数を置く `0080` 以外ほぼ未使用。プロセスあたり約 128〜256B |
| 低位メモリの端数 `0051A`〜`00FFF`(約 2.8KB) | ブロックに満たず未使用(BOOTMAP.md §6) |

### D. BIOS の活用(やり尽くせていない)
カーネルが使っている BIOS は **INT 13h(ディスク)だけ**。使っていないもの:

| BIOS | いま | 使うと | 理由・注意 |
|---|---|---|---|
| **INT 10h**(画面) | VGA を直書き + ANSI を自前解釈 | VRAM 直書き・スクロール・カーソル(console の約 400B)を置き換え。**ANSI の解釈は残る**(BIOS は ESC[ を解釈しない) | 理由は console.c の注記: BIOS が中で `sti` して、IF=0 のカーネル中にタイマの `_isr08` が走り、syscall の途中で切り替わってハングする |
| **INT 16h**(キーボード) | 8042 を直接ポーリング + **JIS 106 配列の表を直書き**(ThinkPad R40 用) | 表(256B)と状態機械(約 500B)が不要。**配列が BIOS 任せになる** | 同上。IRQ1 を PIC でマスクしている(BIOS の INT 09h に取らせない)ので、外す必要がある。**USB キーボード(レガシ・エミュレーション)は INT 16h だけで動く機種がある**(実機 #191 の Eee PC など) |
| INT 14h(シリアル) | 16550 を直接 | 初期化とポーリングの約 200B | 影響小 |
| **INT 1Ah**(RTC) | `date` は 1970-01-01 から数える | **実際の日時で起動**(AH=02/04) | 機能の追加。CMOS の RTC |
| **INT 15h AX=E820h**(メモリマップ) | INT 12h の終端アドレスだけ | **穴や予約を含むレンジ表**が得られる(BOOTMAP.md §4 のレンジ表の入力) | 8086/XT の BIOS には無い → INT 12h にフォールバック |
| **INT 13h AH=08h**(ドライブ幾何) | stage2 の `spt=18` とカーネルの CHS が**ビルド時固定**(FDD=pcat / pcxt で別イメージ) | 1 つのイメージで 1.44MB / 360KB を判別 | |
| **INT 08h のチェーン** | 自前の `_isr08` が INT 08h を**置き換えて**いる。BIOS の旧ハンドラは呼ばない | BDA の tick(0x46C)と**フロッピーのモータ停止タイマ**(BDA 0x440)が進まない → **実機でフロッピーのモータが止まらない疑い**(QEMU では見えない) | 旧ベクタを保存し、18.2Hz 相当(100Hz の約 5.5 回に 1 回)で呼ぶのが定石 *(推定。要実機)* |

BIOS を使うための共通の前提(上の「理由」の根):
**BIOS は非再入で、中で `sti` する。** 今のカーネルは syscall 中に `_isr08` がスロットを切り替えうるので、BIOS の途中で別スロットが BIOS を呼ぶと壊れる(bios13.s の注記にある実害)。
解決は 1 つで足りる: **「BIOS 呼び出し中」フラグ**を持ち、立っている間の `_isr08` は tick を数えて EOI を出すだけで**切り替えない**(または呼び出しの間だけ PIC で IRQ0 をマスクする)。これで INT 10h / 16h / 14h / 1Ah / 13h をすべて安全に使える。

## 3. 64KB の機械に向けた見積もり *(推定。根拠は上の実測)*

カーネルの窓を「実際に必要な分」にして、残りをプールに回す。今の窓は常に 64KB(スタック頂点が `0xFFFE` 固定)。

| 項目 | いま | 減量後(推定) |
|---|---|---|
| text(gc 後) | 22.3KB | FS をドライバへ → 約 10KB |
| syscall スタック | 24.6KB | 4 スロットなら 4KB |
| パイプのバッファ | 4.1KB | 0(プールへ) |
| kwork | 3.5KB | 約 1KB(スロット 4 つ) |
| FS のバッファ | 約 2KB | ドライバ側へ |
| カーネルスタック | 数 KB | 3KB |
| **窓の合計** | **64KB(固定)** | **約 18KB** |

64KB の機械(IVT/BDA/boot info 4KB + 窓 18KB + FS ドライバ約 16KB)だと、プロセスに使えるのは約 26KB(6 ブロック前後)。**ぎりぎり成立する可能性がある**程度の見積もり。
そのためにはカーネルを `0x1000:0000` ではなく**低位(`0x0100:0000` = 物理 0x1000)にロードする**配置にする必要がある。0x1000 に理由は無く慣習である(§3b)が、stage2 との重なりと DMA の 64KB 境界の制約を片付ける必要がある。

## 3b. なぜカーネルは 0x1000 なのか(先に確認したい点)

**リポジトリに理由の記録は無い**(履歴は初期スナップショットに作り直されている)。コードと設計文書から分かること:

- 由来は**最初のスロット方式**: `slot n ↔ セグメント (n+1) × 0x1000`、slot 0 = カーネル = `0x1000`、slot 1〜7 = `0x2000`〜(crt0.s 冒頭の注記、diff/03-boot-mem-sched.md)。つまり「セグメント 0 は IVT/BDA/ブートが使うので、**最初の 64KB 境界の空き**に置き、以後 64KB ごとに 1 プロセス」という配置の**慣習**。
- その後、プロセスは 4KB ブロックのプールになった(#186)が、カーネルの位置とプール先頭 `0x2000`(= 「カーネルの次」)はそのまま残った。**0x1000 でなければならない技術的な根拠は、コードからは見つからない**(リンカスクリプトは 0 起点、`KSEG` は定数 1 つ)。

低位へ動かすときに**実際に効く制約**(以下は私の分析で、リポジトリには書かれていない):

1. **stage2(物理 0x8000〜0x8FFF)との重なり**: カーネルを物理 0x1000 から読むと、イメージが 28KB(0x7000)を超えた時点で、実行中の stage2 を上書きする。今のカーネルは 22〜28KB で境界すれすれ。**解は初期 Linux 方式(下記): stage1 が RAM の終端を INT 12h で調べ、stage2 を最上位 4KB へ読む**。
2. **フロッピーの DMA は物理 64KB 境界をまたげない**(ISA DMA の制約。BIOS の INT 13h はまたぐバッファでエラー 09h を返す)。**対処は軽い**: セクタバッファを 512 バイト境界に揃え、1 セクタずつ転送する(64KB は 512 の倍数なので、またがない)。窓のベースが 512 の倍数(0x1000 など)であることが条件。プロセスのブロックは 4KB 境界なので問題ない。
3. **セグメント 0 の IVT / BDA / boot info**(物理 0x0000〜0x0519)は避ける。カーネルのベースは 0x0600 以降なら足りる。
4. スタック頂点 `0xFFFE` と `KSEG = 0x1000` の定数(crt0.s)、stage2 の jump 先、`x86_slot_seg[0] = 0x1000`(tz/glue.S と src/kexec.c)を、同じ 1 つの値から導く。

### 初期 Linux 方式を取り込む *(Linux 0.01〜0.11 時代の私の記憶。リポジトリでは未確認)*

`bootsect` が 0x7C00 に読まれ、**自分を高位(0x90000)へ移動**し、`setup` を 0x90200、カーネル本体を 0x10000 へ読む。`setup` が BIOS 情報(メモリ量・ディスク・画面)を 0x90000 付近の固定位置に集める。BIOS が要らなくなった所で、`system` を物理 0 番地へコピーして保護モードへ入る。

| 初期 Linux | ia16 での扱い |
|---|---|
| ローダが自分を高位へ退避してからカーネルを読む | **取り込む**。stage1 が `INT 12h` で終端を得て、stage2 を `(kb*64 & 0xFF00) − 0x100`(最上位 4KB。4KB 境界に切り捨て)のセグメントへ読む。64KB 機なら `0x0F00`(物理 0xF000)。カーネルは 0x1000 から最大 56KB(64KB 機)を、stage2 を気にせず読める。起動後、退避先は(位置を boot params で渡せば)プールに戻せる |
| BIOS 情報を固定位置の構造体で渡す | 今の 0x510〜0x519 が原型。構造体にする(#199) |
| カーネルを物理 0 番地へコピー | **やらない**。ia16 は INT 13h のために IVT・BDA が要る。カーネルのベースは 0x0600 以降(ブロックに揃えるなら 0x1000) |
| 保護モード・A20 | 不要 |

つまり**真似るのは「ローダの退避」と「起動情報の構造体」の 2 点**。

つまり**0x1000 は慣習で、動かせる**。動かすコストは上の 1・2・4 を片付けることで、リンカスクリプトの変更ではない。

## 4. 手を付ける順番の提案

1. **gc-sections を既存の Makefile にも入れる**(−2.4KB、リスク小)。
2. **パイプのバッファをプールへ**(−4KB、z80 と同じ方式)。
3. **BIOS 呼び出し中フラグ**を `_isr08` に入れる(INT 13h の安全化にもなる。以降の BIOS 活用の前提)。
4. **INT 08h のチェーン**(実機のモータ停止。実機で確認)。
5. **syscall スタックを実行時のスロット数で確保**(−19KB、crt0.s の変更)。
6. **INT 16h / 10h / 1Ah**(コンソールの減量と、実日時・配列の BIOS 任せ)。
7. **FS のドライバ化**(最大だが設計変更が大きい)。案 E と並べて検討。
8. ブロック粒度を細かく(プロセス側)。

### 6.3 64KB 機の予算(推定)
IVT/BDA/起動情報 4KB + カーネルの窓 約 31KB(text 22.3KB(gc 後)+ data/bss 約 4.5KB+スタック 3〜4KB)+ stage2 4KB(起動後に回収)→ **プロセス用プール 約 28〜32KB(7〜8 ブロック)**。シェル(3 ブロック)+ 小さなコマンド 1〜2 本 + パイプのバッファ。vi やネットワーク系は 128KB 以上に割り切る。

### 6.4 判断が要る点
1. plat.h(TK の未コミット変更)に `#ifndef X86_MAXSLOT` を足してよいか(段階 1a)。足さない場合は、tz のビルドで変換した複製を使う。
2. 段階 2〜4 は crt0.s / stage2.s / sysfile.c / bios13.s といった未コミットのファイルに及ぶ。ブランチを分けるか、`tz/` に写して試作するか。
3. 進める順番。私の推奨は 1 → 2 → 3(→ 4 は実機の確認と並行)→ 5。

### 6.5 訂正と追記(TK の質問への回答, 2026-10-24)

**6.3 の 64KB 予算は gcc の大きさで組んであった。** 全部を tzcc にすると、変換済み 7 モジュールの実測の膨張率 ×1.60(gcc 5,670B → tzcc 9,097B)で、text は 22.3KB → 約 35.7KB(×1.3 でも約 29KB)。64KB 機の窓は約 31KB → 約 44KB、プールは 7〜8 ブロック → **約 4 ブロック**。シェル(3 ブロック)+ 小さなコマンド 1 本が、ぎりぎり。**「gcc 放棄」と「64KB」は、tzcc のコード縮小とセット**:
1. tzcc の出力の小型化(レジスタ割り当て・ピープホール。いまは ax 中心で push/pop が多い)
2. FS をドライバとして外へ(§2B)
3. 使わない機能を捨てる

**gcc が残っている主因は膨張ではなく、tzcc がまだ読めないコードの残り**(前処理後のカーネル 20 ファイル中 8 つがエラー、残りも黙って誤コンパイルする構文がある)と、**量**(未変換の約 18KB + ユーザーコマンド 49 本)。膨張は 2 番目の理由として、64KB で効いてくる。

**`#ifndef X86_MAXSLOT` の注意**: plat.h の値は C(plat.h)・アセンブラ(Makefile の sed → `--defsym X86_N=`)・Makefile.tz の 3 か所で読まれる。`#ifndef` だけ足すと C とアセンブラの値が食い違い、**エラーにならずメモリが壊れる**。同じ変数を両方へ渡すこと、N ごとに OBJ を分けること(make は CFLAGS の変化を追わない)が必須。
